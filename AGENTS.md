# CamelClock — Agent Guide

Next.js 16 (App Router) + Supabase countdown-clock builder. Neubrutalist pixel-art design.

---

| | |
|---|---|

### Naming conventions

- **Components**: PascalCase `.js`, one per file. `'use client'` only where interactivity requires it.
- **CSS**: plain global class names (kebab-case). CSS modules are rare — only `CamelClock.module.css` (and `landing-hero.css`).
- **Utilities/hooks**: camelCase functions; hooks use the `use*` prefix.
- **DB**: tables plural snake_case (`clocks`, `hydrations`, `profiles`); RPCs `snake_case(p_arg)` with named params.

## Working Agreements & Style

### General

- **No comments in code** unless explicitly asked.
- Read the file you're editing and its neighbours before writing. Match existing conventions.
- Prefer editing existing files over creating new ones. Never create docs/READMEs proactively.
- Never re-invent existing components or pickers — reuse them.

### Styling

- The design system is vanilla CSS in `src/app/globals.css`. Components use plain global class names.
- `nbtc` = neubrutalist card treatment (4px border + 8px hard offset shadow), driven by `:root` tokens `--nbtc-border`, `--nbtc-shadow`, `--nbtc-hover-shadow`. Apply to cards and button-like elements.
- Layout limit: `--page-pad-x: 6.0rem`; `.page-container`/navbar and the viewer top row (`.draft-banner-row`) cap at `max-width: 150rem`.
- Multi-state toggles (2+ options, one always active) use `src/components/OptionSlider.js` (`.option-slider`). Don't build ad-hoc pill toggles. *Exception: the navbar theme toggle is a compact Sun/Moon icon button by design.*
- **Press behaviour is centralised** in the shared `button, .pressable, .btn-link, …` rules at the top of globals.css (translate + shadow collapse + transition, plus the disabled state).
- Buttons get the press effect automatically. Non-button interactive elements (`<a>`, `<div>`) must add the `pressable` class — this also suppresses the default link hover underline. Classes already in the shared selector: `.btn-link`, `.account-trigger`, `.edit-fab`, `.social-share-button`.
- Layout breakpoints of note: `@media (max-width:1200px)` restacks the viewer.

### Builder & publish flow

- `CamelClockBuilder` is used on `/edit/[id]` and by nothing else: MORE OPTIONS is gone, no status/embedding/hydration controls, wearables inline below the colours. `/new` uses the multi-step `ClockCreationWizard.js` instead, which shares the `builder-fields/*` inputs and `useClockCreate` hook, not the whole editor. The landing renders the **same** `ClockCreationWizard.js` (it is the single create wizard now), passing `heading`/`subheading` from `landingCopy.js` and relying on the wizard's built-in `AuthModal` fallback for signed-out visitors.
- **Creates always save as `draft`. Edits never touch status — or `viewer_hydrates`.** `useClockCreate` deletes all three of `status`, `boost_order` and `viewer_hydrates` from an edit payload, because the editor carries no toggle for any of them.
- Editing saves redirect to the clock's viewing page; creates land on the viewing page too, carrying `?created=1`, which opens the **"YOUR CLOCK IS SAVED"** confirmation once (the param is stripped after). That dialog is mode `saved` and has **no toggles or settings** — it only confirms the draft exists.
- Live clocks capped at `MAX_LIVE_CLOCKS = 3` (`src/utils/liveLimit.js`; `checkLiveLimit()` returns a `reason`). **Publishing is now a direct write**, gated in the caller: the viewer's draft-banner PUBLISH (`publishClock`) and `ClockCard`'s PUBLISH both call `checkLiveLimit()` then update `status: "live"` themselves. `ClockCard.handleUnpublish` also writes directly. There is no go-live slider anywhere. **Pro/admin are exempt**: `checkLiveLimit()` reads `profiles.is_admin`/`is_pro` for the signed-in owner and returns `{ ok: true }` early, and the DB trigger `enforce_live_clock_limit()` short-circuits for either flag — `is_pro` is written only outside the app (profiles UPDATE is column-gated to `username`), so a client cannot grant itself the cap bypass.
- When `reason === "limit"` → open the waitlist modal (heading "YOU'VE HIT THE FREE LIMIT"), not an inline error.
- The share dialog is **share/embed only** — it never writes `status`. It has three modes: `saved` (heading/subline default to the post-create confirmation, and it renders only a GOT IT button — no link, no settings; reused for the visitor daily-cap modal by passing its own heading/subline), `live` (share link + social row + **EMBED ON SITE** / **EMBED IN NOTION** buttons that open `EmbedSiteModal` / `EmbedHelpModal`) and `welcome` (the `live` block **minus the embed buttons** — the welcome is about the tour — plus the tour's opening copy and **SKIP TUTORIAL** / **START TUTORIAL**; the skip is a small `.text-link`, the start is a bigger green button, `#4caf50` — it opens straight after publishing, so the introduction and the share link live in one place). A caller-supplied `heading`/`subline` always wins over the mode default. No status toggle, no embed-code builder, no owner toggles.
- **`viewer_hydrates` has no UI toggle at all.** Creation always defaults to ON via `buildClockPayload`; because every publish path now writes only `status`, the value is simply carried as-is (and an edit never touches it — `useClockCreate` deletes it). A hydrate-OFF clock can currently only be produced outside the app.
- Waitlist modal copy: `PRO_FEATURES` exported by `Pricing.js` is the single source of truth for Pro feature text.

- **No follow button** — following is fully replaced by hydrating.
- `.viewer-stage` is a 3-col grid `minmax(16rem,1fr) minmax(0,60rem) minmax(16rem,1fr)` and **every child is pinned to its column** (`grid-column: 1/2/3`). Never fall back to auto-placement: a draft renders no `.viewer-info`, so an auto-placed `.viewer-center` drops into the narrow first column and the card renders small on the left.
  - **LEFT** `.viewer-info` (`grid-column:1`, `justify-self:end`, max 26rem): `.community-inline` **plus the share row** (`SocialShareRow` under the stats), all live-only. **Live only** — a draft has no left column at all, so don't put anything there that a draft needs.
  - **MIDDLE** card + `.viewer-center` (`grid-column:2`). The card is the only child — no share row under it.
  - **RIGHT** `.viewer-rail` (`grid-column:3`, `justify-self:start`, 26rem, interaction only, no card wrappers): the HYDRATE/CLAIM button (`.`), the level-vote banner (`LevelPollBanner`, live/open-poll only, directly under the button), `.state`/equip `.level-panel`. No share buttons — sharing moved to the left column.
  - `@media (max-width:1200px)` stacks the cards centred. It resets `grid-column:auto` on `.viewer-info`/`.viewer-center` (an explicit `grid-column:2` against `grid-template-columns:1fr` spawns an implicit second column) and sets `display: contents` on `.viewer-rail`, so the rail **dissolves into the grid** and its children are ordered individually. Order is card (`.viewer-center` 1) → **HYDRATE button (`.clock-post-actions` 2, directly under the card)** → community + share (`.viewer-info` 3) → poll banner (`.viewer-poll` 4) → `.hydrate-error` (5) → `.level-panel` (6). The dissolved rail children get `width:100%; max-width:30rem; justify-self:center` (the rail's own width moved to them). Adding a new rail child means giving it an `order` and that width, since `display: contents` drops the rail's flex gap and width.
- The camel card is deliberately bare: `.card-creator` (avatar + `@handle`) → title → `.clock-finish-row` (the date, dot, and time — no "FINISHES" word) → art → digital row → level banner (live only) → "Create your CamelClock" watermark link (`showWatermark`). The title is a link to the clock's own viewing page whenever `CamelClock` is given a `titleHref` (the viewer passes `/clock/${id}`; the embed passes the absolute clock URL with `titleExternal` so it breaks out of the iframe; the landing's real showcase examples pass `/clock/${id}` with `titleExternal={false}` so they navigate in-tab, while the empty-state fallbacks pass `titleHref={null}` because they have no row). The watermark always points at the CamelClock homepage (`watermarkHref` defaults to `/`; the embed passes the absolute site URL with `watermarkExternal`). No quest bar, no action buttons. The handle lives **in the card, not the rail** — it belongs to the clock, so it survives the ≤1200px restack, and it must not be duplicated in `.viewer-info`. Owners get two absolute corner controls on the card: `.edit-fab` (top-left, purple, → `/edit/[id]`) and `.clock-delete-fab` (top-right, danger red, opens a `ConfirmDialog` then deletes the row and redirects to `/dashboard`).
- Viewer camel passes `hideHydrateNote`. The old `hideQuestProgress` prop is deleted: the level banner+bar is shown on the viewer by default, and `hideLevelBanner` is passed by the **embed** (embeds show title + finish date but no level progress), dashboard ClockCards (they keep the `.level-chip`), and the landing hero. The finish date is `finishRowText` (`formatFinishRow`) and is always smaller than the title: `.clock-finish-row` is `min(1.2rem, calc(var(--clock-scale) * 2.8px))` against the title's `4.2px * --clock-scale`.
- Brand icons live in `.viewer-info` **under** `.community-inline` and its TOP HYDRATORS list: `SocialShareRow` with `showLabel={false}` and `layout="stacked"` — a square top row (WhatsApp / X / Facebook / Email, no Telegram) over full-width COPY LINK / EMBED ON SITE / EMBED IN NOTION action buttons (`onMore` → `EmbedSiteModal`, `onNotion` → `EmbedHelpModal`). **Live only** — a draft isn't shareable, so the row and the rail's HYDRATE-adjacent share controls both stay off. The rail's share buttons (desktop `.post-actions-share` and the old `.mobile-share-button`) are deleted — sharing is left-column only. The rail's HYDRATE button is water-blue (`--water-colour`) and shows no `×N` count; the count lives in the left-column HYDRATIONS stat and the level banner. At ≤1200 the whole share block runs the full width of the community column: the brand squares stretch (`flex:1`, no wrap) and the stacked actions drop their 24.4rem cap — and the EMBED ON SITE button (`.social-share-action-embed-site`) is hidden, leaving COPY LINK + EMBED IN NOTION.
- **VIEWERS CAN HYDRATE is ON by default.** Saved by `buildClockPayload` as `viewer_hydrates: values.viewerHydrates !== false` - an `=== true` test would silently disable hydrations on every new clock now that the builder carries no toggle. Creation ships ON by default (no wizard step asks); publish writes only `status`, so the stored value is carried as-is; an **edit never writes it at all** (`useClockCreate` deletes it from the payload), so re-saving a clock can't undo a deliberate OFF. Hydrate-off clocks render as a pure timer - no level banner, no splash, no interaction, no HYDRATE button; their embeds have no link-out CTA.
- `.community-inline` is public for every visitor: 🔥 HYDRATIONS / 👥 HYDRATORS counts, a `.community-note` banner when hydrations are on, and a TOP HYDRATORS leaderboard — all via the `get_clock_hydrate_stats(clock_id, top_limit)` RPC through `useHydrateStats` (`src/hooks/useHydrateStats.js`, the only caller). Tone/icon picked in ClockViewer via `hydrateNoteText`/`NoteIcon`. The note is now shown to **visitors as well as the owner** (the pool is shared, so "N CLAIMABLE TODAY" is informative for any signed-in hydrator); only an owner below L2 suppresses it, where their own hydrations are free and "no claimable" would mislead. The claim tone is a bright green chip in both themes: light `#43a047` on `rgba(76,175,80,0.22)`, dark `#a5d6a7` on `rgba(76,175,80,0.18)` (`.community-note-claim`).
- Signed-in user with no handle → `.viewer-handle-nudge` "SET YOUR HANDLE" link to `/settings`.
- **Only live `is_showcase` clocks are indexable.** `generateMetadata` on `/clock/[id]` emits `robots: { index: true }` for a live showcase and `noindex, follow` for every other live clock (the draft/missing fallback is `noindex, nofollow`), so a user's clock is shareable by link without ever being published into search. `sitemap.js` mirrors that: it lists the static pages plus live, **unended** showcases (`is_showcase = true`, `target_at > now`) ordered by `showcase_order` — never user clocks. **Never add `/clock` to the robots.txt disallow list** (`robots.js`): a disallowed URL is never crawled, so Google never reads the `noindex` and the page can linger in the index; `noindex` is the only tool that removes it. Flagging a clock as a showcase therefore also means "qualified to appear in search", not just "pinned to the landing".

### Boosts & the hydration economy

- `BOOSTS` in `grids.js` are owner-equipped effects. There are exactly **three categories** — `exercise`, `aura`, `weather` — and a clock may **equip any number** of them. The engine enforces a single **active** overlay per category (a per-category queue rotates the extras), so at most three overlays render at once and `CamelClock`'s single-slot `weather`/`sparkleColour`/`fireworksProgress` assumptions stay valid with no render redesign. `BOOST_CATEGORIES` is the shared order; `boostDefsByCategory()` groups the defs.
  - `exercise` — transforms the body: `pushup`, `jack`.
  - `aura` — pixel shading and sparkles: `shine`, `sparkle`, `fireworks`.
  - `weather` — drawn in `drawing.js`: `sun`, `rain`, `sandstorm`. `rain` is split: `drawRainCloud` (puffy clouds pinned to the top edge) is drawn **before** `drawCamelBoost` so it sits behind the camel, and `drawRainDrops` after it so the drops fall in front. `sun` and `sandstorm` are single post/pre-draw fns.
- **`kind`, `combined`, ambient budgets, `PROPS` and every articulation helper are gone.** A def now carries only `category`, `cadenceMs`, and either an `anim` (`spin`/`pushup`/`jack`/`hop`) or an `overlay` (`shine`/`sparkle`/`fireworks`/`sun`/`rain`/`sandstorm`) or both. Overlays compose; motions queue (one at a time); an overlay whose category is already busy is queued in `startEffect` (`overlayQueues` in `boostEngine.js`) and starts when the category's active one finishes.
- `hop` and `legend` are `reactive: true`. They are reactions, not equipment: `hop` on every hydration, `legend` on a level-up. Reactive defs are excluded from `FREE_BOOST_IDS`/`GATED_BOOST_IDS`, from `boost_order`, and from every picker; `validateBoosts` rejects them in a saved rack. `startReactive` **preempts** — it drops whatever is running or queued so a reaction lands immediately.
- Cadence is one number per def: `cadenceMs` is the whole interval between runs, so the start timer only checks `remainingSec % round(cadenceMs / 1000)`. `shine` is `10000`. Overlays resolve to a pixel-shade fn (`makeShineShade`, `makeSunShade`) or a post-draw fn (`drawSparkles`, `drawFireworks`, `drawSun`, `drawRainCloud`, `drawRainDrops`, `drawSandstorm`) in `CamelClock`'s effect loop.
- **Five levels, and each level reached reveals two effects.** Thresholds are cumulative and 1-based: L1 at 0, L2 at 10, L3 at 50, L4 at 100, L5 at 250. `500` is the top-rung marker — SQL can never pass it into a L6. `MAX_LEVEL = QUEST_LEVELS.length = 5`. No tier names.
- `shine` is the **free level-1 rung**: `startsUnlocked: true`, picked automatically for a new clock, and added by the migration wherever a rack had no aura. The rest are the gated pool.
- **`boost_order` is per clock, not per user.** A flat array of gated ids, dealt at creation and never rewritten, so two clocks at the same level reveal different things. `shuffleBoostOrder()` shuffles *within* each category then deals *round-robin*, which is what guarantees the two ids of a level always span two categories — a shuffle-then-repair pass cannot promise that. It lives on `clocks` (showcase rows included); `random_boost_order()` in SQL mirrors the deal for the backfill. **Every boost id in SQL is lowercase** — `normalise_boost_rack` and `normalise_boost_order` both fold through `upper()` on the way in and emit lowercase on the way out, because the app matches ids literally and uppercase racks resolve to nothing at runtime. Since `20261007120000_lift_category_cap`, `normalise_boost_rack` dedupes by id only — the old one-per-category `rn = 1` pick is gone, matching the lifted cap.
- `boostLadderFor(order)` chunks the order into `UNLOCK_PAIR_SIZE` pairs → `[{ level: 1, ids: ["shine"] }, { level: 2, ids: [a, b] }, …]`. `unlockedBoostIdsFor(order, level)` is the set every picker and the viewer filter use. **Every unlocked helper takes `(order, level)`, not `(count)`** — the ladder belongs to the clock, not the app.
- `categoryProgress(order, level, ownedIds)` drives the viewer's three rows: each bar reads **what fraction of that category has been unlocked**, which is a step function — it only moves when a level hands over a new effect. The viewer passes the `equippable` set as `ownedIds`, so a revealed-but-unwon poll candidate is **not** counted until a vote merges a winner. Do not reintroduce hydration-count progress here; the camel-body hydration bar (below) is the single global count read-out, since every category legitimately shares it.
- `normaliseBoostOrder` is deliberately tolerant: a shorter stored order keeps its thinner last rung, and only a wholly unusable value falls back to `DEFAULT_BOOST_ORDER`. Do not "fix" a short ladder by reshuffling — that would invalidate whatever the owner already equipped.
- Boost/wearable defs carry a **presentation-only `tags: []` array** used purely to group/label in pickers. `wearables.category` is the only functional field — `validateWearables` must key off it. `WEARABLE_CATEGORIES` (`head`/`eyes`/`face`/`neck`/`feet`, one each) is the ordered slot list: `head` hats/helmets, `eyes` eyewear, `face` reserved for facial hair, `neck` chains/ties/medals, `feet` footwear — `eyes` and `face` are currently empty. All four pickers render through `wearablesByCategory()`, which filters out empty slots, rather than walking the `wearables` object; a new item is added by tagging its def with a slot from this list.
- `drawCamelBoost` resolves grid cells to colours and overlays wearable cells **before** the transform, so wearables ride every boost and persist through overlay effects.
- A wearable's `colours` map may hold plain hex **or a CSS custom-property name** (a `--` string, e.g. `"--wearable-ink"`), so dark items (top hat, grad cap) can lighten in dark mode. It is resolved through `resolveWearableColours` (`src/utils/drawing.js`) — once per wearable per draw, never per pixel — in `drawCamelBoost`, `drawWearables` and the reveal-cache builder in `CamelClock`. The dark set is `--wearable-ink` / `--wearable-ink-shadow` / `--wearable-ink-light` in `globals.css` (light ink in `:root`, light-theme-inverted in `.dark`, hierarchy preserved). The reveal cache key includes `themeToken` so a theme toggle rebuilds it.
- Quest helpers in `src/utils/boost.js`: `questState({ count, floorLevel })` → `{ level, next, maxed, countProgress, hydratesToNext }`; plus `levelFromCount`, `clicksToNextLevel`, `hydratesForLevel`, `boostLadderFor`, `unlockedBoostIdsFor`, `boostDefsByCategory`, `categoryProgress`, `shuffleBoostOrder`, `randomBoostSeed`, `normaliseBoostOrder`, `dailyDropQuota()`, `computeDropLeft(dropDay, dropUsed)`, `hydrateNoteText`, `MAX_LEVEL`.
- `useHydrateInteraction(clock, enabled, { isOwner, drop, onBlocked })` owns the whole hydration mechanism. Every counted hydration — click, rack preview, or deferred post-sign-in hand-off — goes through its internal `queueHydrate()`, and every caller (owner and visitor alike) runs the shared-pool check through its internal `spendOrBlock()` first. A level-up fires `triggerNow("legend")`.
- **The daily drop is per user, shared across every clock — and spent by every hydrator, not just the owner.** `user_hydrates (user_id, drop_day, drop_used)` holds one row per hydrator (created on first spend), so hydrating one clock spends the same pool as hydrating another. `hydrate_clock` locks, reads and writes that row **unconditionally** — the owner branch that used to guard the pool is gone, so a signed-in visitor draws on the same ~15–25/day quota as the owner. The quota is `dailyDropQuota()` — **15–25 / day**, varying with the UTC day — resolved server-side in `hydrate_clock` (`v_quota`); the JS mirror exists only for copy, never enforcement. There is no `missed`/carry-over: yesterday's unspent hydrations are gone. The old per-clock `clock_hydrates` table is deleted.
- **The owner's own hydrations are free below L2; a visitor has no free allowance.** `hydrate_clock` gives an owner (`v_is_owner and level < 2`) a free allowance of every hydration up to that clock's 10th (`10 - coalesce(hydrate_count,0)`), and only caps/charges the pool for the overflow, so the first-run tutorial's "hydrate 10 times" step can never be blocked by a shared daily drop the owner spent elsewhere. Hydrations still count normally toward `hydrate_count`/`level`; the `10` mirrors `quest_level()`'s first threshold / `QUEST_LEVELS[0].hydrations`. `useHydrate`'s `spendOrBlock()` mirrors it: the owner's spend/block is skipped while `levelRef.current < 2`, but every other caller (visitor, or owner past L2) checks and spends the pool. Bounded to L2 and (because drafts can't be hydrated + the 3-live cap) a handful of clocks.
- **Hydration (replaces the quest bar).** The camel keeps its hydrate legend as an idle `+` glyph (grid value `9`, rows 62–67 / cols 44–49) that, under an active CTA, darkens to `--pixel-dark` on hover and turns `--water-colour` while a hydration is playing, via `boostIconColour(ctaState, primary, pixelDark)` (`hydrating` → `readWaterColour()`; hover/active → `pixel-dark`; idle → 35% lighten/darken of the primary; else primary). The progress read-out moved **off the camel** into the level banner: the track (`questFilled` / `--per-row`, from `questState(...)`) is **the one global count read-out**. `drawGrid` takes an `iconColour` arg and `drawCamelBoost` bakes the `9` branch into `srcColour` so the `+` rides `pushup`/`jack` transforms. A counted hydration paints a radial water front out of the camel's centre (`makeHydrationShade`, with `spread`/`strength` pushed into `shadeFns`). A level-up is signalled by the `legend` backflip reaction alone. `--water-colour` is a theme token — `#4FC3F7` in `:root`, `#29B6F6` in `.dark`; `readWaterColour()` reads it via `getComputedStyle` (fallback `#4FC3F7`). The theme is the **only** shade: never derive the bar colour from `--primary-colour` or mint a second blue token. `HYDRATION_BAR`, `hydrationPalette` and `paintHydrationBar` are deleted.
- A counted hydration paints a **radial water front** out of the camel's centre: `makeHydrationShade(grid, spread, strength)` returns a per-pixel shade fn (pushed into `shadeFns`, so it composes with shines) that blends every drawn pixel inside `spread × maxRadius` toward `--water-colour` by `0.8 × strength`. The radius expands over the first half of the run and the wash fades back to normal by the end (~675ms — `HYDRATION_SPLASH_MS`, exported from `src/utils/boost.js` so the tour can wait for it); only pixels the grid already has are recoloured, so nothing escapes the camel (`drawHydrationSplash` and its droplet arc are deleted). The full-canvas level-up flood (`hydration-flood` keyframe, `HYDRATION_FLOOD_MS`) is deleted — a level-up now shows only the `legend` backflip, everywhere the clock ticks. The old `.boostProgress*` track/label phases are deleted.
- **Level banner:** `.levelBanner` is the **bottom row of `.clockContainer`** (after the camel + `.digitalRow`, above the watermark) — the viewer camel's level story, gated on `viewerHydrates` (`!hideLevelBanner && viewerHydrates`). It is **transparent** (no box, no inverted background — it must never compete with the camel) and centered on one line: `LEVEL N` label left, a track of **small squares — one per hydration in the current level's span** (`--segments` = `quest.next.hydrations − previous threshold`, so 10 at L1→L2, 40 at L2→L3…) with the already-achieved cells filled `--water-colour` and the rest a faint water outline (`questFilled`), and a `.levelBannerCount` badge right (`{quest.hydratesToNext} TO LEVEL {quest.level + 1}`, or `MAXED` at the top rung). It grids one box per hydration at **`--per-row` = `min(questBoxes, 25)`** and caps the track at **4 rows (100 boxes)**: a span wider than 100 marks each box as more than one hydration (`questHydratesPerBox = ceil(span / 100)`, boxes = `ceil(span / hydratesPerBox)`, filled = `floor(countProgress * span / hydratesPerBox)`) and shows a small **"1 BOX = {n} HYDRATIONS" key** under the boxes. Square size is `max(0.4rem, min(1.5rem, calc(min(24rem, calc(100cqw - (var(--per-row) - 1) * 0.2rem)) / var(--per-row))))` and `.levelBanner` is a `container-type: inline-size` query container with `flex-wrap: wrap` — so a 25-box track keeps its 24rem desktop size and yet shrinks inside narrow cards (e.g. the mobile viewer) instead of overflowing the card. Dashboard cards keep the small `.level-chip` and pass `hideLevelBanner`; the landing hero passes `hideLevelBanner` too. Nothing else in the watermark wrap: it holds only the hydrate note (`.hydrateWatermarkWrap`, not a link) and the "Create your CamelClock" `.watermarkLink`.

### Equipping

- **Equipping has no modal, no SAVE button, and no separate picker.** The only place a clock's show can be changed is the level panel on its own live viewing page.
- **The builder has no boost options at all** — `/new` (the wizard) and `/edit/[id]` show wearables only. Boost equipment is earned, then equipped on the viewing page, so `CamelClockBuilder` just carries `initialBoosts` (`initialClock?.boosts`, else `[{ id: "shine" }]` on create) so the preview still animates what will actually be saved. `BoostBoard.js` is deleted.
- **That also means a draft has no equip UI.** `.level-panel` is gated on `viewerHydrates`, which requires `status === "live"` — equipping happens after publishing. Deliberate, not an oversight. The HYDRATE/CLAIM button is behind the same flag, so a draft or hydrate-off clock renders no button at all rather than a disabled one.
- Each of the three **category rows** in `.level-panel` is EXERCISE / AURA / WEATHER — a tube for each category (any number may be equipped; the engine picks one per category to run) — and the list under its bar is the control. A small `.boost-panel-title` **BOOSTS** heading sits above the category rows so a visitor knows what the chips are:
  - **Owner** → a `<button class="boost-chip">` per effect (`Check` equipped, water-blue `Plus` unlocked, `Lock` + `disabled` locked), `onClick` → `toggleRack`, `onMouseEnter` → `previewRackBoost`.
  - **Everyone else** → the *same* markup as a `<li class="boost-chip readonly">`, neutralised with `cursor: default` plus a `:hover` that kills the press motion. RLS only lets the owner write `clocks.boosts`, so a live control would change optimistically and then silently snap back. Visitors still get the unlock tease.
  - Equipping is **additive** — clicking an unlocked effect toggles it into or out of the rack; a same-category effect never replaces one already equipped. Crossing a level reveals two effects but does **not** unlock them: they go to a community vote (see *Level voting*) and only the winner is merged into `clocks.boosts` by `finalise_poll`. The one-time `.unlock-panel` announcement is deleted — the poll banner is the level-up signal now.
- `toggleRack` keeps **exactly one rack write in flight** (`rackPendingRef` + `rackSaving` disables the rows while it resolves). The whole `jsonb` column is overwritten per write, so overlapping requests could land out of order and drop the newer selection. The optimistic rack is applied to `CamelClock` directly, never "fixed up" into a one-per-category rack.
- Optimistic `rackSelection` feeds straight into `CamelClock` (`boosts={activeBoosts}`, unlocked-filtered) for live preview, an add-diff effect fires `triggerNow(id)`, then `PATCH clocks.boosts` with revert-on-error and `router.refresh()`.
- Dashboard ClockCards were stripped of equip — stats only (`.card-hydrators`, `.card-my-hydrates`).
- A showcase is not equipped any differently — it is just a live clock flagged `is_showcase`, so its rack is equipped on its own viewing page like any other. `/admin/showcases` only reorders (`AdminShowcases.js`), it has no picker.

### Level voting

- **Unlocking is a vote, not an announcement.** Crossing a level reveals the next two gated effects in the clock's `boost_order`, but neither is equippable until the community picks one. A level-up does not open a panel and does not grant anything.
- `hydrate_clock` opens the poll inside the same row-locked transaction that lands the level. Candidates are `revealed_boost_ids(level) − equipped − ids reserved by open polls`, first two in ladder order; a single survivor opens a one-option poll (the second slot is left null rather than re-offered later). `revealed_boost_ids(p_order, p_level)` is the SQL mirror of `unlockedBoostIdsFor` — `x.ord - 1 < (least(coalesce(p_level,1),5) - 1) * 2` — and is a cheap seed; the merge itself goes through `normalise_boost_rack`.
- `clock_polls` (one row per poll, `option_a`/`option_b`, `votes_a`/`votes_b`, `winner`, `resolved_at`, `closes_at` = now + 24h) is **tallies-on-the-row**. `closes_at` is the **maximum** window, not a fixed one: `poll_ready()` also settles a poll early once `POLL_QUORUM` (10) total votes are in with the two sides disagreeing and the poll has been open at least `POLL_MIN_OPEN_SECS` (30 min). A **tutorial** poll (below) has its own rules: it settles at **2 total votes** (`poll_tutorial_quorum()`), so the owner casts one and has to share the clock to bring in a second voter. `poll_tutorial_min_open_secs()` is 0, so the second vote resolves it immediately, and `poll_tutorial_window_secs()` is the ordinary 24h fallback — if nobody else votes, the poll settles with the owner's single vote (or with no winner if nobody voted, re-offering the candidates at the next level-up). There is **no instant close on the first vote** and no short countdown. `clock_poll_votes` is primary-keyed `(poll_id, user_id)` — one row each; `vote_poll` upserts that row, so a signed-in voter can **switch their choice any time until the poll closes**, the tally moving by the delta (old −1, new +1). A Realtime subscription carries lifecycle and counts when it delivers, but it is **not** the only path: `clock_polls`' select policy reads through `clocks`, and Realtime can miss those events, so the viewer also **refetches on every level change** — watching both the confirmed `level` and the optimistic `levelFromCount(hydrateCount)`, then retrying 1.5s later, because the count can cross the threshold before `hydrate_clock`'s debounce + commit creates the poll — which is exactly when a poll is born) and **on a slow 8s timer while any poll is open**.
- **`clock_polls`/`clock_poll_votes` have no client write path.** `finalise_poll` (definer, owner-only EXECUTE) tallies, stamps the winner (`votes_a > votes_b ? a : b`, ties broken at random, 0 votes → no winner) and merges a winner into `clocks.boosts` via `normalise_boost_rack`; `finalise_due_polls()` sweeps every poll `poll_ready()`. Both are scheduled **and** called by `get_clock_polls` — the only public read, and the only thing a client invokes, so a stale page still resolves a missed poll on its next read. `finalise_due_polls` may be wired to `pg_cron` later without any other change. `vote_poll` never merges — it only coerces the vote, so the resolution/lock order stays `clocks` → poll.
- `useClockPoll(clockId, enabled, { onResolve })` (`src/hooks/useClockPoll.js`, the only caller) owns fetch + Realtime + a 1s tick + `vote()`. Because the `clock_polls` Realtime INSERT/UPDATE is unreliable (its RLS reads through `clocks`), ClockViewer also calls the returned `reload()` whenever `level` rises — the exact moment a poll is created — and the hook re-`load()`s on a slow 8s timer while any poll is open. The 1s tick makes the client call `get_clock_polls` when a row's `closes_at` passes. First sight of a winner is announced through `onResolve` (ClockViewer `router.refresh()`), so the owner's rack picks up the merge without a manual reload; `onResolve` never fires on the initial load.
- **Everyone signed in can vote — visitors and the owner alike.** `LevelPollBanner` (`.level-poll-*`) lives in `.viewer-rail`, directly under the HYDRATE button — it only ever renders at rail width (26rem), so its option rows stack. It renders one card per open poll: option buttons whose water fill is the share of the tally, a real `CLOSES IN` countdown for ordinary polls (a **tutorial** poll swaps it for `{total}/2 VOTES` and a sub-line telling the owner to share for a second voter), a quorum meter (`.level-poll-quorum*`, `votes so far / POLL_QUORUM`) for ordinary polls (the tutorial poll omits the meter in favour of that copy), a preview `mouseenter`/`focus` → the same `triggerNow` path the rack preview uses (and `mouseleave`/`blur` → the camel ref's `stopNow`, so lifting the cursor drops the effect at once), and a "SIGN IN TO VOTE" affordance that opens the AuthModal. A voter can click the other option to switch (the selected one carries `.is-mine`); `useClockPoll` keeps one `vote_poll` in flight per poll so a fast switch can't land out of order, and `vote()` re-`load()`s after a successful vote so a decisive quorum settles the poll immediately. A resolved poll flashes its winner for `RESOLVED_FLASH_MS` (12s) then clears.
- **Equipping is gated strictly on `winner`.** The viewer narrows the rack through `wonIds` (every `poll.winner`), so a revealed-but-not-yet-won effect renders as an unreachable chip even if its id somehow lingers in an optimistically-held rack; `toggleRack` guards `!equippable.has(id)`. `equippable = revealed − candidates-in-open-polls` winnowed by `wonIds` — so `activeBoosts` only ever feeds `CamelClock` effects the owner has actually earned or won.
- Losing an option is **not** a dead end: the loser is not equipped and is re-offered as a candidate at the next level-up (candidates are recomputed fresh each time). No re-run, no vote history UI.

### First-run tour

- The tour is a **state-driven spotlight** over the owner's own clock (`ClockTour.js`), shown on **every live clock until that clock has been toured** — completion is per clock (`clocks.tutorial_completed`), never per account, so a new clock always opens the tour again. **A draft never opens the tour**: publishing is explained by the **"WHAT HAPPENS WHEN YOU PUBLISH?"** note under the draft banner's PUBLISH button (a `<details>`/`<summary>` in `ClockViewer` — plain text, collapsed by default, deliberately *not* a `<button>`, which would pick up the shared press motion), and `page.js` only sets `showTour` once `status === "live"`. On a live clock it shows while `clocks.tutorial_completed` is still false and the clock is below L2 or holds a tutorial poll.
- **All tour copy lives in `src/content/tour.js`** (a `welcome` block plus a `steps` map keyed by rung id, mirroring `landing.js`) — edit strings there, no component change. The rung ids are load-bearing (they pick the target and the gating); the surrounding prose is safe to rewrite.
- **The rungs are dynamic, and there is no welcome rung.** The list is `hydrate → levelbar → (vote → rack) → daily → share`. The two boost rungs exist **only once the derived level reaches 2** (`questState({ count: hydrateCount }).level` — the poll is born in the same transaction as the level-up, so the count is the source of truth), and the tail rungs join **only after both boost rungs have been seen**. Between the second drink and level 2 there is no rung to show, so the tour renders **nothing at all** — no tip, no scrim, no buttons — and comes back when the level-2 poll lands. The welcome copy instead opens the **post-publish share dialog** (`ShareDialog` mode `welcome`), so the introduction and the share link live in one place: **PUBLISH → welcome dialog (share block + SKIP TUTORIAL / START TUTORIAL) → mini steps**, no reload. A fresh load of an untoured live clock starts straight into the mini steps. In the welcome dialog **SKIP TUTORIAL is a small text link** (`.text-link`) and **START TUTORIAL is the loud control** — a bigger green button (`#4caf50`, the same green as PUBLISH). The **welcome mode carries no embed buttons** — it is about the tour; `EMBED ON SITE` / `EMBED IN NOTION` live in the `live` mode and in the viewer's left-column share row.
- The rungs point at real elements: `hydrate` → the **camel itself** (`CamelClock`'s `camelArtRef`, fallback card), `levelbar` → the **LEVEL N label** (`CamelClock`'s `levelLabelRef`, fallback `.levelBanner`, then card), `vote` → the poll banner (`LevelPollBanner`'s `rootRef`, fallback `.level-panel`, then card), `rack` → the whole `.level-panel`, `daily` → the left-panel `.community-note`, `share` → the **share buttons** (`SocialShareRow`'s `rootRef`, fallback `.community-top`). The tour has **no stored step**: it keeps a `seen` set of rung ids and the current rung is the first unseen one. That set is persisted per clock in `localStorage` under `camelClock.tourSeen.<clockId>` (read in an effect after mount so server and client markup match; folded with the derived gates on every write), so a reload cannot replay the tail.
- **The gated rungs are derived, never stored — and they carry no button.** `hydrate`, `levelbar` and `vote` are the steps the reader can *do*: the tour moves on when the action lands, so the tip shows a live status line instead of a NEXT button. The state comes from the clock, not from a stored step, so nothing has to be set in an effect (the React `set-state-in-effect` rule is an error in this repo):
  - `hydrate` → done once a drink has **finished playing**, not the moment it lands: the tour keeps a `settledCount` that only advances `HYDRATION_SPLASH_MS` (675ms) after the count moved, so the next tip never lands on top of the splash. A tap on the camel *or* the rail button both land.
  - `levelbar` → done once the **second** drink has finished playing — the level tip steps aside after the reader's next click, so the camel is never buried under a modal. It also completes the moment the clock reaches level 2. Until then the tip counts down from the live count: `"{count} MORE CLICKS AND YOU'RE LEVEL {level}"`, where `count = QUEST_LEVELS[0].hydrations - hydrateCount` (so two drinks landing at once correctly reads 8).
  - `vote` → done once the poll is settled (`resolved_at`) **or the reader has cast their own vote** (`my_choice`, tutorial included) — the boost may stay locked until the poll resolves, but the reader has done their part and the tour must never stall waiting for a second voter.
  - `rack` and `daily` are copy-only and keep a real, pressable **NEXT** button (`.clock-tour-primary`); **only `share` carries DONE**. This is deliberate: `rack` is the last rung before the tail exists, so treating it as the last rung would show DONE and skip `daily`/`share` entirely. **The `idle` branch is gone** — the tour used to render `null` once the camel was tapped, which hid the whole thing.
- **The tour can end two ways.** SKIP TUTORIAL stamps the clock and closes — it is a small **text link** (`.text-link`), not a chunky button, and there is no X icon any more. DONE appears only on `share` (the true last rung, reachable once the boost and tail rungs exist). There is **no GOT IT / soft exit**, and `ClockViewer.finishTour()` only ever receives `"skipped"` or `"done"`; both stamp `complete_tutorial`.
- The scrim **never captures pointer events** — the highlighted control stays usable underneath. It darkens **and greyscales** (`backdrop-filter: grayscale(1)`) the whole viewport, and the target is lifted above it via a `.clock-tour-peek` class (position + z-index bump), so exactly one control stays lit *in colour* and no neighbouring element glints through an area-based hole; when a target can't be measured the tip centres instead. **The tip itself never takes the pointer either** (`.clock-tour-tip { pointer-events: none }`, its buttons take it back): a short viewport can push the tip back over the camel, and the camel has to stay tappable — the level step is only finished by tapping it. `ClockViewer` owns `showTour`/`tourOpen` and the target refs (`card`/`camel`/`poll`/`panel`/`level`/`levelLabel`/`title`/`daily`/`top`/`share`) it hands to `ClockTour` as `targets`. The **level step measures the `LEVEL N` label but lifts the whole `.levelBanner`** with `.clock-tour-peek`, so the water-coloured boxes stay in colour rather than only the plain label. **The vote/rack tips are anchored to the left of the rail** (`left = rect.left - TIP_GAP - tipSize.w`, vertically centred, clamped; falls back to below/above centring when there is no room) so the poll/rack and the camel preview stay visible while the tip still reads as "near the boosts". The tip draws a small border-only **speech-bubble tail** (`.clock-tour-tail` + `-top/-bottom/-left/-right`) on whichever side faces the target.
- **The drink tip sits over the card; the level tip sits beside the label.** The drink step's tip is centred horizontally on the card with its **bottom aligned to the title's bottom** (`titleRef`), so it covers the creator row + title and stops above the art; its target is still the camel, so the tail points **down at the camel**, which stays tappable. The level step's tip is pulled back by the pointer's reach so the **tail's point lands at the LEVEL N label's left edge** (a slight card overlap) without covering the start of the word; when there is no room beside it (the ≤1200px stacked card) it drops under the label instead.
- **The tour steps out of the shot while the reader's own animation plays.** `CamelClock` reports it through `onAnimatingChange`: true for the hydration splash, the `hop`/`legend` reactions and a boost the reader previewed by hand (tracked in `previewIdsRef`), and **false for the clock's own ambient cadence** — the ambient effects must never blink the tip out. While it is true the tip gets `.is-hidden` (`visibility: hidden` — hidden, not unmounted, so it keeps its box and the measured placement stays valid) and the scrim gets `.is-colour` (greyscale off, dim softened to 0.25), so the effect is seen in full colour instead of behind a grey filter. `ClockViewer` holds the flag as `camelAnimating` and passes it to `ClockTour` as `animating`.
- **Two geometry rules the tail and the tip depend on.** (1) The tail is a 2.4rem square rotated 45deg sitting at a **negative offset** on `.clock-tour-tip`, which must **not** carry `overflow` (the scroll lives on the inner `.clock-tour-tip-inner` wrapper) or the tail is clipped. The offset is **-1.8rem**: absolute offsets resolve against the tip's *padding box*, so the tail's centre has to clear the 4px border — 12px of half-square plus 4px of border. The along-axis position is `targetCentre - tipEdge - 4px - 12px`, clamped to the tip's edge. The side is chosen by comparing the two centres (**`|dx| > |dy|` → left/right, else top/bottom**), not by the old largest-gap test, so a slightly overlapping target (the daily note, the level label) still gets a correctly-aimed tail. (2) `.clock-tour-tip-inner` needs `overflow-x: hidden` **and** a hidden scrollbar: `overflow-y: auto` alone implies `overflow-x: auto`, and the shared button hover-translate (8px right/down) then opens a horizontal scrollbar on the tip.
- **Post-publish timing.** Publishing flips `status` client-side, but `showTour` is a server-computed prop that was `false` on the draft render, so `useState(showTour)` never re-syncs and the tour only appeared on a full reload. `publishClock` now opens the share dialog in **welcome mode**; START TUTORIAL (or simply dismissing it) opens the tour for a live, not-yet-toured clock, no reload. The tour also re-opens itself when the **tutorial poll appears** (edge-triggered on `polls.some(p => p.tutorial)`, so a hidden gap never fights it).
- The tour hides itself while a dialog is open (`shareOpen` — the live/welcome share dialog or the post-create `saved` dialog). The skip control reads **SKIP TUTORIAL**.
- Finishing or skipping fires `track("tour_completed", { skipped, lastStep })` (`skipped` is true for SKIP TUTORIAL; DONE sends `skipped: false`) and calls `complete_tutorial(p_clock_id)` (definer RPC, `authenticated` only, owner-gated — stamps **that clock's** `tutorial_completed = true`); the tour closes immediately and the write is best-effort. `clocks.tutorial_completed` is **never** written by an edit — re-saving a clock leaves its tour state alone, and a skipped clock's own L2 poll just uses the normal quorum rules.
- `hydrate_clock` marks the level-2 poll `tutorial = true` when **that clock's** `tutorial_completed` is still false, so a freshly-created clock's first poll is its owner's to settle at **2 votes**. The owner's own vote is one; a second voter (brought in by sharing) settles it. The `closes_at` value is the ordinary 24h fallback (`poll_tutorial_window_secs()`), `poll_tutorial_min_open_secs()` is 0, and `poll_ready()` never closes it on the first vote. (`profiles.tutorial_completed` was dropped in `20261016120000_tier1_dead_columns.sql` — the per-account design is fully gone.)

### Auth & email

- **Email confirmation is enforced.** Signup never auto-logs-in — the modal swaps to a **"CHECK YOUR INBOX"** panel (`MailCheck` icon, `.confirm-check`) confirming a link was sent to the entered address, with `emailRedirectTo: ${window.location.origin}/auth/confirm`. `SignUpForm` hands the address to `AuthModal` via `onAwaitingConfirm(email)`, which decides the panel vs the form.
- Confirm/reset pages are **button-gated**: the single-use token is consumed only on button press (`verifyOtp({ token_hash, type })`, with an `exchangeCodeForSession(code)` fallback).
- `/auth/confirm` → `ConfirmForm.js` (`type` defaults `"signup"`); `/reset-password` → `ResetPasswordForm.js` (defaults `"recovery"`), which reveals the form only after the gate passes.
- **Changing your password needs an email code (Secure password change).** `SettingsView` is a two-step client flow: NEW PASSWORD + CONFIRM → **SEND CODE** (`supabase.auth.reauthenticate()`, which emails a 6-digit code) → CODE → **UPDATE PASSWORD** (`supabase.auth.updateUser({ password, nonce })`). It no longer uses the old `changePassword` server action (removed from `settings/actions.js`). Requires **Secure password change** enabled in the Supabase dashboard (Auth → Providers → Email) and a **Reauthentication** email template.
- **Pending-clock stash**: the builder writes `{ ...values, payload: buildPayload(values) }` to localStorage key `camelClock.pending`; `savePendingClock` in `ConfirmForm.js` auto-inserts it after confirming, forcing `status: "draft"`. On failure it keeps the stash (re-using the link retries) and shows an inline "couldn't be saved" notice. The stash also carries an optional **`handle`** (stashed by `SignUpForm` on the no-session path) which `savePendingClock` writes to `profiles.username` after confirming (a `23505` collision is non-fatal — the handle just falls back to Settings) and reports as `track("handle_set", { source: "signup" })`.
- **The dashboard shows a handle nudge** until a handle is set or dismissed: `DashboardView` takes `hasHandle` (server-fetched `profiles.username` in `dashboard/page.js`) and renders `.handle-nudge` (`.handle-nudge-cta` → `/settings`, `.handle-nudge-dismiss` → `localStorage` key `camelClock.handleNudgeDismissed`).
- Only signed-in users can hydrate. A signed-out click on the camel opens the AuthModal with `next` back to the clock; the deferred-hydrate flow fires once the visitor signs in.
- Root layout renders no global navbar — **each page must include its own `<Navbar />`** (e.g. `src/app/settings/page.js` mirrors `new/page.js`).
- SMTP via Plunk (custom SMTP is free in Supabase). Plunk's dashboard SMTP tab is the source of truth for host/ports (STARTTLS 2587 / SSL 2465). Supabase sender `no-reply@camelclock.com`, name `CamelClock`, 60s throttle / 30-per-hr.
- Email templates are neubrutalist HTML with the logo hotlinked as `{{ .SiteURL }}/logo.png`. confirm = `{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=signup`; reset = `{{ .SiteURL }}/reset-password?token_hash={{ .TokenHash }}&type=recovery`; reauthentication (Secure password change) has **no link** — it shows the 6-digit `{{ .Token }}` the settings form asks for. Site URL flips `http://localhost:3000` ↔ `https://camelclock.com`.
- Navbar shows a signed-in live-count pill (`N/3`, `Rocket` icon, `.nav-live-pill`); clicking opens the waitlist modal. It is a single green pill with `:hover`/`:focus-visible` neutralised.

### Handles

- `profiles.username` is the only public identity field; a row may have none (no handle = not on leaderboards).
- DB-enforced `^[a-z0-9_]{3,20}$` + case-insensitive unique index (`profiles_username_lower_idx`).
- Changes go through `updateUsername` in `src/app/settings/actions.js` (`createClient`; returns "That handle is taken." on `error.code === "23505"`). Validation lives in `src/utils/usernameValidation.js` (`validateUsername`/`normalizeUsername`, lowercases). The settings page server-fetches the current handle. A handle can also be chosen at signup (an optional field on `SignUpForm`, written on the confirm path) and changed in Settings; both routes fire `track("handle_set", { source })`.

### Embeds

- `/clock/[id]/embed` is the **only** frameable route — `next.config.mjs` excludes it from `X-Frame-Options`/`frame-ancestors`. Don't duplicate that route or the exclusion.
- Theme from `?theme=light|dark` (default light), card from `?card=card|transparent` (default card), size from `?size=sm|md|lg` (default `sm`), host flag from `?notion=1` (default off). Legacy `?theme=transparent` auto-maps to `light` + `transparent`.
- Theme/card/size/host come from the URL params **once** (`?theme=`/`?card=`/`?size=`/`?notion=`), applied by `EmbedMode` (body/html classes) plus the no-flash head script. There is **no on-screen toggle** — the old hover `OptionSlider` pills (`.embed-theme-switch`) and EmbedShell's URL-sync state are deleted, so viewers can't change an embedded clock's theme. `size` maps to `--embed-card-max` (`sm` 30rem / `md` 44rem / `lg` 60rem) which caps `body.embed-mode .public-clock-card`'s width — a Notion block only grows the camel as far as the chosen size before it letterboxes. The viewer card keeps its own 60rem (the cap is embed-scoped).
- **The embed page paints no background of its own.** `body.embed-mode` is `background-color: transparent`, so a website sees the host page through **both** card styles: CARD renders just the card (border/shadow/padding intact) and TRANSPARENT strips those too. Transparency can't cross a cross-origin iframe on Notion (a transparent frame there reads as white), so the Notion embed URL carries **`?notion=1`** — emitted only by `EmbedHelpModal`, never by `EmbedSiteModal` — which adds `body.embed-mode.embed-notion` and paints the host's page colour: `#ffffff` on light, `#191919` on dark. Web and Notion styling must stay split this way: don't put `#191919` back on `.embed-transparent`, or website transparency breaks again.
- Narrow embeds keep the camel filling the card: `.clockContainer` padding/gap are `clamp(...vw, ...)` so insets shrink with the width, and `body.embed-mode` trims `.public-clock`/`.public-clock-card` padding at `@media (max-width: 520px)` (which tracks the iframe's own viewport). Don't reintroduce large fixed-rem padding inside the clock — it squeezes the art out of proportion at small widths.
- The site footer is hidden inside the embed via `body.embed-mode`.
- An embed shows the title and the finish date (`finishRowText`, always smaller than the title) but **no level banner or hydration progress** — `EmbedClock` passes `hideLevelBanner`. It is a pure timer **and a doorway**: tapping the camel never hydrates in place (the embed lives in a cross-origin iframe where the Supabase session cookie is not reliably sent, so an in-place tap could only ever produce a sign-in wall at peak intent). The tap instead fires `track("embed_tapped")` and `window.open(absolute /clock/${id}, "_top")` — out to the clock's own page, where hydration and the signup flow work properly. `EmbedClock` therefore holds **no hydration machinery at all** — no `useHydrateInteraction`, no `AuthModal`, no cap `ShareDialog`, no `entitlements` prop; `/embed` reads no drop pool and `EmbedShell` passes none. Its title links out to the clock's own page with `target="_top"` (`titleHref` defaults to the absolute `/clock/${id}`; a caller with no page passes `null`), and its watermark points at the homepage (`watermarkHref={siteUrl}` + `watermarkExternal`).
- The embed help modals are destination-specific, never the generic ShareDialog: `EmbedSiteModal` (`EMBED ON YOUR SITE` — a wide two-column sheet: theme/card/size `OptionSlider`s + embed URL/iframe code left, a mock webpage right) and `EmbedHelpModal` (`EMBED IN NOTION` — theme/card `OptionSlider`s that rewrite the `/embed` URL live and always append `&notion=1`, defaulting to DARK + CARD with no `size` param so it falls to the 30rem `sm` default, then Notion steps). They open from the viewer's left-column share row and from the ShareDialog's **EMBED ON SITE** / **EMBED IN NOTION** buttons. The site modal's preview is the **real** `/clock/[id]/embed` iframe in the selected theme/card, floated top-right in a mock blog article whose inline text bars wrap around it (newspaper style — left and below); the frame itself is chrome-less (`border: none`) because the embed draws its own card border, and its height is set tall enough that the card is never clipped. The mockup chrome re-declares the light/dark tokens locally (`.embed-mockup.light`/`.dark`), so the host page theme never moves. Both show the `/clock/[id]/embed` URL and rely on the same `share-field`/`embed-help-*` classes.

### Landing page

The landing is a **flat page** — no GSAP, no scroll-linked animation library, no `.scroll-container`, no `?section=` plumbing, no `locked` class; the Navbar's `handleSectionNav` just does a `scrollIntoView` (and `router.push('/#id')` when off the landing). The hero is scroll-*driven* (sticky CSS + an `IntersectionObserver`), which needs no dependency.

Order: `Navbar` → `LandingHero` → `ClockCreationWizard` (wizard) → `ExampleGrid` → `Pricing` → global footer. The wizard comes *before* the examples on purpose: what you can build, then what other people already built. **Showcases live in `clocks`** — the old `showcases` table was folded in and dropped (`20261014120000_clocks_showcase.sql`): `page.js` reads `clocks` where `is_showcase = true` and `status = 'live'`, ordered by `showcase_order`, and hands the rows straight to `ExampleGrid`. When that query is empty or throws, `makeFallbackClocks()` supplies hardcoded rows (fake `0000…` ids, `is_fallback: true`) whose boosted racks are filtered through `unlockedBoostIdsFor(FALLBACK_ORDER, level)` against their own `hydrate_count`, so the empty-install examples only show effects they have actually revealed. The hero is **not** one of these rows (it is hardcoded in `LandingHero`), so there is no `is_hero` flag or single-hero split any more.

- `.landing-page` caps the landing at 124rem. The shared `.page-container` runs to 150rem because the viewer and admin sheet need it; don't raise the landing to match or the hero clock spans the whole display on a laptop.
- Showcases are managed from `/admin/showcases` (`src/app/admin/showcases/page.js` lists `clocks` where `status='live'` and `is_showcase`, ordered by `showcase_order` then `hydrate_count`; `AdminShowcases.js` is a small reorder table — ORDER/CLOCK/TARGET/HYDRATIONS with up/down arrows). The page only **orders** what is already flagged — flagging a clock (`is_showcase = true`) is done directly in the database, so `set_clock_showcase` was dropped (`20261015120000_drop_set_clock_showcase.sql`) and only `reorder_showcases(p_ids)` (admin-gated definer RPC, called by `reorderShowcases`) remains. A showcase row stores exactly what any clock does (`target_at`, `intro_text`, `celebration_message`, `celebration_type`, colours, wearables, `boosts`, `boost_order`, `hydrate_count`, `level`, `viewer_hydrates`) — there is no `feature_title`/`feature_body`/`is_hero` any more.
- **A showcased clock is forced hydratable.** The `enforce_showcase_hydrates()` trigger (`20261015130000_showcase_hydratable.sql`) sets `viewer_hydrates = true` on any row where `is_showcase`, so a showcase's viewing page (and its landing card) always offers HYDRATE.
- **Hero** (`LandingHero.js` + `landing-hero.css`): a 2-column grid — sticky showcase right, scroll track left, `align-items: start` (**not** `center`, or the stretched grid item has no room to travel). The showcase carries **no card treatment at all** (no `.nbtc`, no background), deliberately matching `/clock/[id]/embed?card=transparent` so the camel sits directly on the page grid. Colours are passed as `CamelClock` props; the landing must **never** mutate root colour variables. At ≤1200 this grid collapses to a single stacked column — see the simple-mode bullets below.
- **The hero is one camel that gets built up, not a carousel of camels that get swapped.** `HERO_STEPS` in `LandingHero.js` is the whole script — five steps, each carrying its own copy and what it adds. It is hardcoded deliberately: it is one bespoke sequence, not N interchangeable records, and its identity (title, date, colours, wearables) is hardcoded in `HERO_CLOCK` in the same file rather than read from a showcase row.
- **Layer order in `HERO_STEPS` is load-bearing, not cosmetic.** Colours must land before wearables (CamelClock draws one reveal or the other, not both), and boosts must land after both, because CamelClock's reveal path early-returns *before* `drawCamelBoost` — anything moving under a filling pixel layer is silently dropped.
- `useHeroBuild` (`src/hooks/useHeroBuild.js`) turns the step index into reveal progress. Layers now follow the scroll in both directions — going backwards drops later layers outright — while colours arrive once on page load and stay. A hard flick counts skipped steps as they arrive.
- **The hero camel is hydratable on every slide** — `LandingHero` always passes `viewerHydrates` + `onHydrateClick={hydrate}` (only the watermark stays gated on the built step). `useShowcaseHydrate` (`src/hooks/useShowcaseHydrate.js`) counts **taps alone** (`hydrateCount = taps`), with no build-driven floor: CamelClock renders whatever rack it is handed (`activeBoosts = boosts`, no level filter) and the hero hides the level banner, so a floor would only ever fire a stray blue splash when the build equips a boost. Every tap paints the water front, and a tap crossing a threshold fires `legend` instead of `hop`.
- The intro is a **direct grid child** (`grid-area: copy-intro`, 100vh), not a child of `.hero-copy-track`. `.hero-copy-track` holds a pinned accordion pane and the invisible geometry that drives the scroll. (Desktop branch only; at ≤1200 the intro/camel/tail stack — see below.) 
- The features are an **accordion**: all titles are always visible in a sticky pane (`.hero-copy-pane`) beside the camel. Clicking a title scrolls to its sentinel via `goTo(i)`. The body opens with `grid-template-rows: 0fr → 1fr` and no JS height measurement, so the pixel-font copy reflows cleanly. Sentinels (`.hero-sentinel`) carry `data-showcase-step="<i + 1>"`; the intro carries none, so the observer's initial 0 remains "nothing built yet". **The scroll distance per section is the sentinel height (130vh) plus a 60vh tail** — deliberately more than a viewport, because there is no snapping to catch an overshoot and the sentinel height is the only thing preventing a fast flick from skipping a layer of the build.
- The rule under each row is that step's **progress bar**: `border-top` stays as the track and a `::after` fill in `--primary-colour` draws over it via `width: calc(var(--p) * 100%)`. `useShowcaseSteps` writes `--p` **straight onto the DOM nodes, never into state** — it updates every scroll frame, and routing it through `setState` would re-render the accordion at 60fps, re-rendering the open panel whose `grid-template-rows` transition must not be disturbed. Progress is measured against the same 50% midline as `OBSERVER_MARGIN`, so a bar reads 0 as its step opens and 1 as the next takes over. The fill is offset by `top: -4px` because a border sits outside the padding box.
- **There is no scroll snapping anywhere.** The old `useSlideSnap` is deleted; an accordion opens whatever the reader reached rather than skipping, so snapping bought nothing and cost the reader their scroll gesture. Don't reintroduce CSS `scroll-snap` either — it fights the gesture. Title clicks still navigate, via `scrollToStep` in `useHeroSentinels`, which measures on demand so a webfont reflow can't leave a click aiming at a stale offset.
- **At ≤1200px the whole cinematic build is dropped for a plain stacked page** (`landing-hero--simple`). `LandingHero.js` holds a `simple` state driven by `matchMedia('(max-width: 1200px)')`; it starts `false` — matching the server's desktop markup — and live-swaps on resize. In simple mode `buildIndex = simple ? HERO_STEPS.length : index`, so the camel is built to its final state at once and runs its ambient cadence with tap-to-hydrate; the demo-run effect, the step-5 `preview()` effect and `handleCtaClick` all early-return on `simple` (the CTAs become native anchors). The features render as ordinary sections (`.hero-features`/`.hero-feature`) with the same copy as the accordion, each carrying its step `id` as the DOM id so a `#occasion` CTA jumps to it.
- **Simple mode reorders the intro**: the `<h1>` goes first, then the camel directly beneath it, then the lede and CTAs in `.hero-intro-tail`. A phone sees what it can build before the paragraph. `LandingHero.js` builds the title, lede, CTAs and camel as extracted nodes (`titleNode`/`ledeNode`/`actionsNode`/`stageNode`) so both layouts place the same nodes; the cinematic branch keeps title+lede+CTAs together in `.hero-intro`.
- The ≤1200 shell — a plain flex stack, the camel unstuck, the sentinels `display: none` — lives in a single `@media (max-width: 1200px)` block in `landing-hero.css`, because the pre-hydration/no-JS desktop markup needs the identical thing. It **must** set `align-items: stretch` on `.landing-hero`: the base rule's `align-items: start` (for the desktop grid) left-aligns every flex child and sizes it to content, which left the camel narrow and off-centre. The hero's `padding-top` there also clears the fixed navbar (`--navbar-clearance` minus the body's `--page-pad-y`).
- `useShowcaseSteps` (`src/hooks/useShowcaseSteps.js`) tracks the active step by observing those sentinels. `goTo` is called with a 0-based row index from the accordion and translated to the 1-based step for scroll targets. The dots and arrows were removed in favour of the clickable accordion titles. It no-ops in simple mode, where the sentinels do not exist.
- `useHeroSentinels(count)` (`src/hooks/useHeroSentinels.js`) owns the track ref and the `scrollToStep` a title click uses; it always centres the target. There is no pinned ≤1200 branch any more — the sentinels are hidden there and the accordion is desktop-only.
- `CamelClock`'s wearable reveal cache is **keyed on the wearable ids** (`sig`), exactly like the body-pixel cache above it. It is also what makes the wearables step land on the *hero's* hat rather than one frame late.
- Step 5 fires `preview()` exactly once, guarded by a ref — `celebrate` stays true for every render after it latches and `preview()` is not idempotent.
- **Examples grid** (`ExampleGrid.js`): `.example-grid` / `.example-card` are global classes in `globals.css`, not a CSS module. Each card's `CamelClock` is only mounted once the card is within 400px of the viewport, because every clock runs its own countdown interval and boost engine — starting five at once buys five animation loops for art nobody is looking at. A real showcase is a live clock, so its title links to `/clock/[id]` in-tab (`titleExternal={false}`); an empty-state fallback (`is_fallback`) has no row, so it passes `titleHref={null}` and `showWatermark={false}` and renders as a bare timer.

- **Wizard** (`ClockCreationWizard.js`) is the single create wizard, used by **both** the landing and `/new` — the landing passes `heading`/`subheading` (from `landingCopy.js`) and shows the heading itself; `/new` renders its own `page-heading` and passes nothing. It is a four-slide form — Title → When → Colours + wearables (one slide) → Label/completion text (the last slide, where the CREATE button lives; there is no separate "done" slide). Question text and the default title come from `landingCopy.quickStart` (`steps` / `defaults.title`). Submission goes through `useClockCreate`, so it always lands as a `draft`. It carries no boost controls, so it submits `boosts: [{ id: "shine" }]` (a module-level `DEFAULT_BOOSTS`) to put every wizard clock on the free rung, and its live preview uses that same rack so what you see is what gets saved. No hydration question: creation always ships `viewer_hydrates` ON via `buildClockPayload`'s default. `/new` redirects signed-out users to `/login`, so its `AuthModal` fallback only ever fires on the landing, where the stash-for-confirm flow (`savePendingClock`) needs it.

### Analytics & privacy

- Analytics is **Umami Cloud**, cookieless. The script is injected in `layout.js` via `next/script` (`strategy="afterInteractive"`) **only when `NEXT_PUBLIC_UMAMI_WEBSITE_ID` is set**, with `data-domains="camelclock.com"` (so local dev and preview builds never pollute stats) and `data-do-not-track="true"`.
- **Debug/experiment endpoints are gone.** Self-hosting the Google font is what removed the last third-party runtime request; the only remaining third-party requests are Umami, Stripe (B1), and provider-hosted assets.
- **Every event goes through `track(event, data)` (`src/utils/analytics.js`)**, which no-ops unless `window.umami` exists and swallows its own errors. The nine events are `wizard_started`, `clock_created`, `clock_published` (`{ source: "viewer" | "dashboard" }`), `embed_copied_site` (`{ kind, size, theme, card }`), `embed_copied_notion`, `embed_tapped` (embed camel tap → out to the viewer), `upgrade_clicked` (`{ source }`), `tour_completed` (`{ skipped, lastStep }`), `handle_set` (`{ source: "signup" | "settings" }`). **The north-star metric is embeds copied per week.**
- **Never pass personal data to `track()`** — no emails, handles, clock titles, ids, or user-entered text. Fixed event names plus ids/booleans/enums only. A new event must follow the same rule.
- **Adding cookies/tracking restores the consent requirement.** The site currently needs **no cookie banner** because (a) Umami stores nothing on the device — no cookies, no localStorage, sessions derived from a rotating salted hash, IP not retained — so PECR's consent trigger isn't met, and (b) the Data (Use and Access) Act 2025 adds a "statistical purposes" exception permitting consent-free analytics *for statistics/improvement only*, provided analytics is disclosed and there is a free objection route (we honour DNT). **The moment you add advertising, profiling, personalisation, GA4 with Google Signals/ad features, Microsoft Clarity, or session replay/heatmaps, the exception is lost and a banner becomes mandatory.** Umami's replay/heatmap features must stay OFF for this reason.
- `privacy/page.js` is the source of truth for the disclosure: it names Supabase, Netlify, Umami and Plunk as processors, states the lawful basis (contract / legitimate interests / statistical purposes), the transfer safeguards (UK Addendum / EU SCCs), and the public-clocks notice. Keep it in step with the processors actually in use — Stripe arrives in B1.
- The **IndexNow key file** lives at `public/<key>.txt` (contents = the key), used to ping Bing for new showcase URLs. It is not a secret.

## Boundaries & Guardrails

### Security — RLS and database

- **RLS is ENFORCED on `clocks`, `hydrations`, `profiles` and must stay that way.**
- **Never add `FORCE RLS`** — it breaks the service-role cleanup in `deleteAccount`.
- Policies: `clocks` — anon SELECT only `status='live'`; authenticated SELECT `status='live' OR user_id = auth.uid()`; INSERT/UPDATE/DELETE owner-only via `user_id = auth.uid()` (with `WITH CHECK`). `hydrations` — owner SELECT only; no client INSERT/UPDATE/DELETE (hydration is permanent, `hydrate_clock` is the only writer). `profiles` — owner read-only; UPDATE column-gated via `REVOKE UPDATE` + `GRANT UPDATE (username)`. All other writes owner-only.
- **All `SECURITY DEFINER` functions pin `search_path`.**
- `get_clock_hydrate_stats(clock_id, top_limit)` is the **only** thing exposing other users' row data publicly. It must **never select email/user_id**. Read it through `useHydrateStats` only — never call the RPC directly from a component.
- `get_clock_creator(p_clock_id)` returns only `username`.
- `hydrate_clock(target, amount)` is the **only** writer of `clocks.hydrate_count` / `level` / `hydrator_count` / `owner_hydrate_count`. It row-locks `clocks` up front, opens the level poll when the level rises (flagging it `tutorial = true` for a clock whose own `tutorial_completed` is still false), spends the caller's per-user `user_hydrates` row (free for an owner's first 10 on a sub-L2 clock), and returns `{ hydrate_count, level, drop_day, drop_used }`.
- `user_hydrates` is RLS owner-select-only (`user_hydrates_select_own`); `hydrate_clock` is its only writer. `clocks.tutorial_completed` is never written by an edit — only the definer `complete_tutorial(p_clock_id)` (authenticated EXECUTE, owner-gated) sets it.
- **`clock_polls` / `clock_poll_votes` have no client write path.** `finalise_poll` (definer, owner-only EXECUTE) is the only writer of a poll's `winner`/`resolved_at` and the only thing besides the owner that writes `clocks.boosts` (it merges a winner through `normalise_boost_rack`). `get_clock_polls` is the only public read (definer, pinned `search_path`); `vote_poll` is authenticated-only and one row per `(poll_id, user_id)`. RLS on `clock_polls` mirrors `clocks` visibility; `clock_poll_votes` is owner-read-only with no client INSERT.
- `count_my_live_clocks()` only counts `auth.uid()`'s rows, so it can't leak other users' counts.
- The trigger `enforce_live_clock_limit()` is the hard backstop for the 3-live cap: `SECURITY DEFINER`, pinned `search_path`, skips non-live inserts and live→live updates, bypasses for admins via `profiles.is_admin`, raises `Live clock limit reached (3)` at >= 3 other live rows.
- Service-role table GRANTs on `hydrations`/`clocks`/`profiles` are required for `deleteAccount` (`src/app/settings/actions.js` via `createAdminClient` in `src/lib/supabase/admin.js`). On `permission denied for table hydrations`, re-run the GRANTs — **don't** switch to `FORCE RLS`.
- Owners can never touch `is_admin`.

### Never do these

- **Never let server- or client-supplied data set `status: "live"`** outside the `checkLiveLimit()` gate. The pending-clock stash insert is always forced to `draft`.
- **Never carry a client-supplied status** into `savePendingClock` — a tampered localStorage stash could otherwise publish without the limit gate.
- **Never auto-verify an email token on page load** — the token is single-use and email clients prefetch links. Button-gate it.
- **Never expose email, `user_id`, or other users' rows** through a new query or RPC.
- **Never introduce a second `quest_level` overload** — one pure SQL `IMMUTABLE` function mirroring `QUEST_LEVELS`.
- **Never add a client write path to `clock_polls`/`clock_poll_votes`**, and never let a client write a revealed-but-unwon boost into `clocks.boosts` — the rack is gated on `poll.winner`, and only `finalise_poll` may merge a winner.
- **Never derive poll resolution (quorum/deadline) in the client.** `poll_ready()` / `finalise_due_polls()` are the source of truth; the JS `POLL_QUORUM` / `POLL_MIN_OPEN_MS` exist only to render copy.
- **Never let the first-run tour write `status` itself** — the tour only starts once a clock is live and has no publish step or action button; PUBLISH goes straight through `checkLiveLimit()`, so the 3-live gate still applies, and `clocks.tutorial_completed` is only ever stamped by the definer `complete_tutorial(p_clock_id)`, never by an edit.
- **Never let JS and SQL drift**: `QUEST_LEVELS` ↔ `quest_level(bigint)` (1-based: level = thresholds passed + 1); `dailyDropQuota()` ↔ the `v_quota` expression in `hydrate_clock`; the free-sub-L2 owner allowance (`QUEST_LEVELS[0].hydrations` = `10` in `hydrate_clock`'s owner branch ↔ `levelRef.current < 2` in `useHydrate`'s `beginHydrate`); and `POLL_QUORUM` / `POLL_MIN_OPEN_MS` (`src/utils/polls.js`) ↔ `poll_quorum()` / `poll_min_open_secs()`, the SQL source of truth the JS mirrors purely for copy.
- **Never guess DB columns** — read the newest migration first.

### CSS guardrails

- **Never re-declare `box-shadow` on a component state** (e.g. `.boost-chip.available`). Set `--nbtc-shadow` instead — a raw `box-shadow` at higher specificity beats the shared `button:hover` collapse and makes buttons slide instead of press.
- **Never re-declare `transition`, `transform`, `:hover` press styles, or `:disabled`** on an individual component. The shared rules own all press motion and the disabled state.
- **`.text-link` is the one documented exception.** A quiet action that should not read as a button (the tour's SKIP TUTORIAL) uses the shared `.text-link` class, which drops the button chrome *and* the press motion — it carries its own `:hover` rule because `button:hover` (0-1-1) outranks a bare class. Use that class rather than hand-rolling another opt-out.
- Global gotchas: `button:hover { transform: translate(8px,8px) }` moves every real button; `a:hover { text-decoration: 4px solid underline }` underlines every link. Interactive anchors that shouldn't look like links need `pressable` or an explicit override.
- Don't reference a `.nav-live-pill.at-cap` variant — it doesn't exist; the pill is a single green pill.
- Don't "fix" the clock watermark's save CTA — it deliberately keeps the standard link underline on hover instead of the press animation.
- An embedded clock is themed by its URL params only — there is no on-screen theme toggle (the `.embed-theme-switch` pills are deleted). Set theme/card via `EmbedMode` (body/html classes) rather than new CSS entry points.

### Data & rendering guardrails

- **Never call `getComputedStyle` or `Date` in render.** Reveal progress is passed as a prop and inlined as a custom property so server and client match.
- **Never walk `hydrate_count` backwards** — `applyCount` never decreases; `serverCount` (which only moves on a confirmed server value) drives the stats refetch.
- Keep **exactly one `hydrate_clock()` request in flight**. Clicks during a request accumulate and are sent when it resolves, so responses can't arrive out of order and clobber newer entitlement state. The owner-spend a request covered is **subtracted**, not zeroed.
- **The daily pool is spent before `onBlocked` fires** — no phantom `+1` when blocked. `onBlocked` branches by viewer: an **owner** opens the ShareDialog in grow mode ("SHARE TO KEEP GROWING") and sets the inline cap nudge; a **visitor** gets the water-toned `.hydrate-error.hydrate-capped` inline notice in the rail plus a `ShareDialog mode="saved"` cap modal (heading "THAT'S TODAY'S HYDRATIONS"). The one exception is a sub-L2 clock (see the free-sub-L2 bullet in *Boosts & the hydration economy*): there `spendOrBlock` skips the spend and block entirely, so the tutorial can't be capped.
- **Never hardcode per-anim physics in `drawCamelBoost`** when a `def.profile` exists — read it purely from `def.profile` (`pivotX`/`pivotY`, `reps`, per-row `rowScale`, etc.).
- For `ghost`, alpha **must** stay the terminal transform (applied after the `shadeFns` chain in `CamelClock`) — `lightenHex` silently breaks on `rgba(...)`.
- `.hydrated-card` border/shadow is `hydrated && !owned` gated. **Hydration is permanent** — the old UNHYDRATE button (a client delete of the `hydrations` row) is gone and the `hydrations` delete/insert policies are dropped, so a `hydrations` row can never be removed from the app or the Data API (it would otherwise reset the lifetime self-hydrate cap and drop the hydrator from counts). `hydrate_clock()` (definer) and `deleteAccount` (service role) still write it because both bypass RLS.
- The "SUPPORTED" stat card counts **others'** clocks you've hydrated (`followedClocks` minus own ids) — never a clock state, always third-party.
- Dashboard hydrate stats come from `clocks.hydrate_count` + the denormalised `clocks.hydrator_count` (maintained by `hydrate_clock()`) — the dashboard needs no RPC, because RLS on `hydrations` is owner-gated. Per-hydrator counts use `hydrations.hydrate_count`; `clocks.owner_hydrate_count` splits out the owner's own claims.
- There are no guest-hydrate storage/caps, no welcome-gift column, no `boost_events` trail, and no double-hydrate hour.

- Never commit secrets or keys.
